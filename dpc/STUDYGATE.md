# 学习闸门（StudyGate）

> 让手机也跟着 WorkBuddy「学习目标管理台」走：**到了放行时段，如果今天的学习目标还有没打卡的，就不解锁，继续冻结。**

v1.9.0 起提供，v1.9.5 补上「保护已失效」提示，v1.10.3 加上关键应用名单，1.49.4 起记忆闪卡不再参与联动（只认打卡目标与禁忌惩罚）。

## 它解决什么

原来的逻辑只有一条时间表：到了放行时段就解冻，跟你今天干了什么无关。
于是有个明显的漏洞——**22:00 一到，抖音自动放出来，哪怕今天的目标一个没动**。

学习闸门在时间表之上再加一层：按时间表该放行了，但学习台说"今天还有目标没打卡"，
就继续冻结，直到你打完卡，或者闸门区间结束。

## 数据从哪来

手机没有 WorkBuddy 环境，也不该把资料库的鉴权 token 塞进 APK。所以走**中转**：

```
WorkBuddy 学习台(云端表)
     │ 每 15 分钟
     ▼
PC 端 study_sync（check_study.py）
     ├──▶ study.flag        （PC 引擎用）
     └──▶ push_gist.ps1 ──▶ GitHub secret Gist 的 study-gate.json
                                  │ 手机每 ~10 分钟 GET raw
                                  ▼              （secret gist 的 raw 免鉴权）
                             StudyGate
```

`study-gate.json` 只有六个字段，扁平结构：

```json
{"date":"2026-10-22","enabled":true,"start":"22:00","end":"23:00",
 "allDone":false,"pending":1,"checkedAt":"2026-10-22 21:12"}
```

手机端只做**消费者**：它不写、不登录、不持有任何凭据。

## 生效条件

四条**全部满足**才继续冻结：

| 条件 | 说明 |
| --- | --- |
| `enabled` | PC 面板里「目标没打完就继续屏蔽」开着 |
| 数据是今天的 | `date` == 今天 |
| 数据没超龄 | `checkedAt` 在 45 分钟内 |
| 此刻在区间内 | 当前时间落在 `start`–`end`（支持跨午夜） |
| `allDone == false` | 今天还有目标没打卡 |

任一条不满足 → 退回纯时间表，正常放行。

## 为什么是「读不到就放行」

这是刻意的（fail-open），和 PC 端同一套约定：

- 从没拉到过数据（新装 / Gist 被清）→ 放行
- JSON 损坏、字段缺失 → 放行
- 日期不是今天（PC 昨天推的）→ 放行
- 超过 45 分钟没更新（PC 关机 / 断网）→ 放行

**宁可保护不生效，也不能因为电脑没开就把人锁死。**
代价是"保护可能悄悄失效"，所以 v1.9.5 把它显式化了——见下。

## 界面上看得见

手机首页有独立的「学习联动」卡片，六种状态：

| 状态 | 文案（第二行） | 颜色 |
| --- | --- | --- |
| 生效中 | 今天还有目标没打卡，22:00-23:00 继续冻结 | 红 |
| **保护已失效** | 学习进度 90 分钟没更新，PC 端可能没开机 | 红 |
| 保护已失效（跨天） | 进度还停在 2026-10-21，PC 端今天没在推 | 红 |
| 待命 | 今天还有目标没打卡 · 22:00-23:00 到点继续冻结 | 正常 |
| 已打卡 | 今天目标已全部打卡（22:00-23:00） | 正常 |
| 已关闭 / 无数据 | PC 端没开 / 暂无数据 | 次要灰 |

「保护已失效」这一态单独存在，是因为数据过期时 `shouldHold()` 返回 false（fail-open），
只看它的话界面会显示"到点继续冻结"这种乐观文案——用户以为有人在管，其实没有。

## 哪些应用受闸门管：关键应用名单

闸门**不是**对黑名单里所有应用生效的。`Rule.gate` 决定一个应用会不会被延长冻结：

- 新应用的默认值按"每天总共能放行多久"猜：≤ 6 小时算娱乐（`gate=true`），
  更长的算日常工具（`gate=false`）
- 猜错了由用户改：黑名单页底部「🔒 关键应用名单」，勾上的就是 `gate=false`

**为什么不让程序自己判断得更聪明？** 自动识别的误判代价不对称——
把工作软件判成娱乐，结果是工作时间被锁死；把娱乐判成工作，只是少管一个。
前者严重得多，所以名单交给用户维护，默认值只当起点。

名单没有单独存储，直接由 `Rule.gate` 反推（`RuleStore.keyApps()`）。
存两份状态必然会不同步：在编辑器里关掉开关、名单却没变，这类 bug 最难查。

v1.10.3 实测的一个例子：Voyage 工具箱（放行 21:00-00:00）放行时长 3 小时，
被自动判成娱乐，于是 22:00-23:00 之外也被闸门延长冻结，直接影响工作。
加入名单后它只按自己的时间表走，午夜该冻还是冻 —— 只是不再被学习目标牵连。

## 黑名单按规则折叠

批量设完时段之后，十几个应用各占一行、副标题一模一样，翻起来又长又分不清。
v1.10.4 起按 `Rule.groupKey()` 折叠：

```
┌────────────────────────────────────────┐
│ 6 个应用                        全部冻结 ▸│
│ 放行 每天 22:00-23:00                    │
│ 抖音、哔哩哔哩、红果免费短剧 等              │
└────────────────────────────────────────┘
        ↓ 点一下展开
│   抖音                          冻结中    │
│   哔哩哔哩                       冻结中    │
│   …                                      │
│   改这一组的时段                          │
```

- 分组键 = 放行星期 + 每段时段 + `gate`。**`gate` 必须算进去**：
  行为不同的应用合在一张卡里，卡上写的"关键应用"会对其中一部分撒谎
- 段的先后顺序在构造 `Rule` 时已规范化，不影响分组
- 只有 1 个应用的组不折叠，否则每个应用都得点一下才看得见
- 组头只报汇总（全部冻结 / 全部放行 / 5-10 冻结），明细在子行里各自显示
- 组内带「改这一组的时段」，不用回顶部重走「批量设时段」
- 展开状态在重建后保留；改完/套用完自动展开结果那张卡

## 手机上打卡：本机就是学习台

打卡不再走 Gist 中转。手机自带目标（`StudyStore`），打完一笔就落本机
`study.json`，闸门在同一进程里当场重判：

```
打卡页 ──上推──▶ StudyStore.check() ──▶ 写 study.json
                        │
                        ├─▶ StudyGate.invalidate ──▶ Guard.apply（当场解冻）
                        └─▶ Hub.markStudyDirty ──▶ 推 checkin-ledger.json（后台）
```

判定只看一份快照：`enabled` + `allDone` + 数据新鲜度。

### 老队列的补丁都已删掉

`checkin-queue.json` 时代要等 Gist 往返才知道"补齐了"，于是有 `pendingAfter`、
`mergePending(remote, local)`、`noteLocalPending()` 三件套。v1.31.0 起：

- 数据就在本机文件里，`StudyStore.save()` 直接触发 `invalidate`，没有延迟可补
- 队列链路（`CheckinStore` / `CheckinSync` / `patchQueue`）整体删除
- `ST_QUEUED`（等 PC 记账）状态一并消失，首页按钮后缀不再有"等电脑记账"

上传是另一件事，不影响闸门：见 [CHECKIN.md](CHECKIN.md)「手动上传」。

## 手机端没有开关

`enabled` 由 PC 端下发，手机上没有任何开关可以关掉学习闸门。
想关只能回电脑改，和「黑名单只进不出」是同一设计哲学：
**绕路只有一条，而且不在手机上。**

## 调试

```bash
# 拉取是否成功、当前是否 hold
adb logcat -s AFS | grep study-gate

# 正常应看到类似
# I AFS: study-gate fetched: hold=false allDone=false enabled=true

# 服务节拍是否活着（每 5 分钟一条）
adb logcat -s AFS | grep "tick alive"
```

关键参数都在 `StudyGate.java` 顶部：

| 常量 | 默认 | 含义 |
| --- | --- | --- |
| `GIST_ID` | 见文件 | 同步 Gist 的 id（换了要重编译） |
| `STALE_MS` | 45 分钟 | 数据超龄线，超过就不参与冻结 |
| `REFRESH_MS` | 10 分钟 | 拉取节流间隔 |
| `FETCH_LIVENESS_MS` | 30 秒 | 单次拉取卡死兜底（DNS 不受连接超时控制） |

## 测试

判定与文案全是纯函数（不碰 `android.*`、不用 `org.json`——它在 `android.jar` 里是 stub），
所以能在 JDK 上离线跑：

```bash
bash test/run.sh     # 186 项，含闸门 40+ 项、分组键 9 项、禁忌待办 9 项、按钮文案 6 项
```

覆盖：区间判定（含跨午夜）、好/坏 JSON、日期错、超龄、`error` 字段、
六种卡片状态、分组键（同规则同键 / 时段或 gate 不同必须不同键 / 段顺序无关）、
以及"过期时绝不能显示乐观文案"这类断言。

注：`BuildConfig` 是构建期生成的（真 token 只在 `build.sh` 里注入），
`test/run.sh` 会自己生成一份空 token 的，所以离线回归不需要 `token.local`。
